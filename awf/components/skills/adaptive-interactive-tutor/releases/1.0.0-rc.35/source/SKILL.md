## When to Use

- The user wants to learn or master a single concept, paper, skill, codebase, multi-cluster mega-project, or entire academic/technical discipline through interactive questioning (`TDD`) or continuous quiz-first grilling (`GRILL`)—especially when the source PDF omits foundational domain background.
- The user wants to **co-evolve/improve a scheme through interactive tutoring (`Tutor-Driven Design` / `以教代建`)**, **be briefed & quizzed on both mechanism and slide design (`Grill-Driven Design` / `烤问出题`)**, or **have the Agent build the HTML-PPT head-down first (`1-Slide-Per-Step`) with full background onboarding and then dual-upgrade both the PPT and `AWF HTML-PPT` after human review (`AUTONOMOUS_DUAL_EVOLVE`)**.
- The user explicitly invokes `AWF Tutor`, `SciTutor`, `tutor`, `ait`, `导师`, `以教代建`, `烤问模式`, `grill`, `GDD`, `闷头做完再改`, `tutor-ppt`, `认知PPT`, or mentions Socratic learning, Feynman technique, Scaffolding, POE, Case Method, PBL, or Bloom's taxonomy.

## Workflow Steps

### Step 0: Beyond-PDF Background Gap Audit (`domain_background_bridge`), Plain-Language Primer + AI Value Triage (`ai_value_triage`), Reader-Intent / JIT Mode Triage (`TDD` vs `GRILL` vs `AUTONOMOUS_DUAL_EVOLVE`) & `slide_manifest.json`
1. Audit omitted foundations in the source PDF/project (`pdf_omitted_background_gaps` $\ge 2$) and deliver a 3–5 sentence plain-language onboarding primer (`outside_pdf_onboarding_primer`) + 3-line Value-vs-Routine Triage (`ai_value_triage`: 全篇真王牌 / 前置台阶 / 常规快进区, zero internal AWF codewords!) **before** asking Stage 0 MCQs or station questions. Frame emphasis choices around reader intent or dynamic `JIT_DURING_GRILL` discovery rather than raw paper module names, and **NEVER ask any Slide-Count MCQ ("页数怎么选") or preset fixed total slide counts**—slides grow purely by logic and need!
2. Synthesize the **4-Rung Zoom-In Background Funnel** (`four_rung_funnel`: macro stakes $\to$ canonical working principle + custom SVG/interactive visual plan $\to$ $\ge 2$ core jargon translations $\to$ prior-art trade-off deadlock), dedicating $\ge 3$ `V2/V3` opening slides on full-paper decks ($\ge 10$ slides).
3. Initialize `slide_manifest.json` via `audit_single_slide_step.py --init-storyboard` (and/or `--record-background-bridge`).

### Step 1: Station Execution (Mode-Specific)
- **If Mode 1 (`TDD`)**: On opening background stations, teach the canonical working principle & everyday analogies first (`beyond_pdf_background_synthesis`, zero premature paper-recipe trivia), then unpack the 7-element anatomy via Wittgenstein's ladder, ask one Socratic `[ ? ]` question, capture the user's orthogonal insight, and record `tdd_station_capsule` (`--record-tdd-capsule`).
- **If Mode 2 (`GRILL` / Briefing-First Dual-Stage GDD)**:
  1. **Mechanism Grill**: On foundation/background stations, use `"FOUNDATION_INTUITION_BUILD"` and present `background_briefing_anchor` FIRST before posing the 3-Part Anchored `grill_question`. If the user says `"不会"` or misses, immediately teach via Wittgenstein's ladder (`Teach-on-Miss`) and pose an **Isomorphic Re-Grill question** (`teaching_and_regrill_closure`; never ask *"听懂了吗"*).
  2. **Slide Design MCQ**: Map the grilled bottleneck to the slide centerpiece (`bottleneck_to_slide_mapping`) and present a plain-language **Multiple-Choice Question (`slide_design_mcq`: A/B/C with `(Recommended)`)** asking how `slide_{k:02d}.html` should be visually structured. Record `gdd_grill_capsule` (`--record-grill-capsule`).
- **If Mode 3 (`AUTONOMOUS_DUAL_EVOLVE`)**: Execute head-down 1-slide-per-step synthesis starting with the $\ge 3$ `V2/V3` 4-Rung background onboarding slides without interrupting the user.

### Step 2: Atomic Implementation & Single-Slide Gatekeeper (`skill.anti-goodhart-verification@3.7.0-rc.7` + `skill.html-ppt@1.0.0-rc.24`)
Build and audit strictly 1 capsule / 1 slide (`slides/slide_{k:02d}.html`) per step via `audit_single_slide_step.py`, enforcing applicable per-slide DesignAG checks (`D1`–`D16`, including custom SVG/interactive `V2/V3` visuals on background slides and zero leaked framework meta-jargon) and the 1-Hop topological lock before unlocking `slide_{k+1}`.

### Step 3: Deck Assembly, Human Review & Post-Review Dual-Evolution (`apply_human_feedback_dual_upgrade`)
Assemble the verified deck (`--assemble-deck`) and present **both** `Z:\path\to\deck.html` and `file:///Z:/path/to/deck.html`. When the user provides review feedback, run `--apply-feedback-dual-upgrade` to simultaneously patch/re-audit the PPT slide(s) and record/evolve the corresponding gate + negative canary in `AWF HTML-PPT` / `AWF DesignAG`.

## Gotchas

- **Never rely solely on the raw PDF for background! Always synthesize outside-PDF domain world knowledge (`domain_background_bridge`), plain-language analogies, and custom `V2/V3` SVG/interactive schematics across the 4-Rung Funnel (`>=3` opening background slides on full-paper decks).**
- **Never print AI self-scaffolding / rubric meta-labels (`背景导读第 1 阶`, `宏观产业痛点`, `Rung 1`, `伏笔回收`, `交互实验 #3`) or `<18px` visible HTML / `<22px` hollow `space-between` HD text cards on slides (`D3` & `D6`).**
- **Never leak internal AWF framework codewords (`V0–V3`, `Stage k.2`, `UNBOUNDED_FLOW_DRIVEN`, `JIT_DURING_QA`, `gdd_grill_capsule`, `slide_manifest.json`) in user-facing dialogue, MCQs, grill prompts, or slide copy.**
- **Never ask any Slide-Count MCQ ("页数怎么选 / 做多少页") or preset fixed total slide counts! Let total slide count emerge purely from logical closure and cognitive need (`UNBOUNDED_FLOW_DRIVEN` automatically, omitting `total_slides_mcq`).**
- **Never ask an unread-PDF user to blindly pick unfamiliar paper module names (`"以下哪些模块需要作为重头戏展开讲"`) at Stage 0! Deliver `ai_value_triage` first and offer Reader-Intent lenses or `JIT_DURING_GRILL` dynamic focus adjustment, plus `trunk_context_preview` when peeling Onion trunks.**
- **Never cold-ambush users in `GRILL` mode or quiz paper-specific recipes (`BCP/Ag`, `PDISNN`) on Slide 1 in `TDD` mode before establishing how the baseline device/system works (`background_briefing_anchor` / `beyond_pdf_background_synthesis`).**
- **Never bolt unanchored 3-card bare-noun bottom strips (`电子密度 Q 峰` / `热振动椭球 ADP` / `精修残差因子 R1`) beneath diagrams to pad canvas coverage (`D3`, `D4`, `D6`, `D8`, `D16`, `D18`); prefer single-tier full-height visuals or explicit step-callout bridges, verified by the Anti-Collusion Zero-Context Blind Reader.**
- **Always delegate code/scientific anti-shortcut verification to `skill.anti-goodhart-verification@3.7.0-rc.7` (`AWF Guard`, 74 sub-checks) and visual/pedagogical/PPT verification to `skill.design-anti-goodhart@1.0.0-rc.22` (`AWF DesignAG`, 18 gates) + `skill.html-ppt@1.0.0-rc.24` (Tri-Mode 1-Slide-Per-Step).**
- **Never unlock or implement a downstream `@scientific_atom` or `slide_{k+1}` while `slide_k` has not achieved `PASS` (`unverified_hop_distance == 1`).**
- **Always output both Windows native (`Z:\...`) and browser (`file:///Z:/...`) paths for HTML deliverables.**

## D17/D18 evidence hardening contract (2026-11-20)

Resolved composition: Tutor Skill/Workflow `1.0.0-rc.35`, DesignAG Skill/Workflow
`1.0.0-rc.22`, HTML-PPT Skill `1.0.0-rc.24` / Workflow `1.0.0-rc.21`,
Guard `3.7.0-rc.7`, repository verifier `1.0.0-rc.2`.

1. D17 no longer invents missing grades. All 15 knowledge criteria, all B-E
   grades, five dimensions, readability penalties and R1-R7 assessments are
   explicit. Weights and required modalities are fixed to the co-located rubric;
   NaN/Inf, booleans as scores, negative counts, duplicate criteria and out-of-range
   values fail. The threshold cannot be below 80; final HTML-PPT requires 85.
   Any redline prevents acceptance even if the numerical score remains high.
2. D17/D18 require separately authorized Ed25519 renderer and reviewer receipts.
   The runner supplies its public-key trust policy, expected artifact paths and
   run ID outside the user bundle. There are NO default trusted production keys.
   Never auto-trust a key embedded in a submission or copy test authorities into
   production. A trusted runner and isolated signer keys are the security boundary.
3. Receipts bind the exact HTML and PNG bytes, capture profile, static slide
   selector/index/state, complete frame coverage, complete rubric payload and
   31 criterion observations. Missing/corrupt/non-PNG/wrong-size images, altered
   source, copied PNGs across frames, stale run IDs, unsigned edits, unknown keys,
   same renderer/reviewer key and partial review coverage do not pass.
4. Supported profile is `offline-static-slide-initial-v1`: normalized explicit
   html/head/body; exact offline CSP from `design_capture_profile.CSP_META` as a
   direct head child before active content; all resources embedded as data/inline
   content; no executable scripts or event handlers. Duplicate attributes and
   non-void self-closing tags are rejected (use explicit SVG closing tags too).
   Static `.slide` elements are
   counted from actual HTML; each initial frame must be captured. Without `.slide`,
   the single `html` frame is used. Identical PNGs across frames require additional
   review. JavaScript-generated views and interaction state coverage are unsupported
   by this profile and remain REVIEW_REQUIRED, not automatically accepted.
5. Structural assembly is a draft milestone. HTML-PPT's per-slide path runs ten
   applicable checks; `assemble_verified_deck` reports `presentation_acceptance:
   REVIEW_REQUIRED`. Final acceptance uses `--verify-deck-evidence` and all 18 gates.
   Direct `run_all_18_design_gates` also rejects bundle HTML that differs from the
   actual reviewed artifact. No alternate public entry point may bypass binding.

### Trust and domain limits

Signatures prove who attested to which bytes; they do not prove a renderer executed
correctly, an auditor truly looked, scientific truth, or independence of judgment.
The renderer must actually capture each declared frame; the reviewer must inspect
the captures and record observations. D1-D16 still accept some caller-supplied
metadata. This release tests force-PASS mutations for D17/D18, not all 18 gates.
The fixed knowledge rubric is the bundled optoelectronic rubric; adapting it to
another domain requires an explicitly reviewed rubric successor, not caller-chosen
weights. Guard scientific validation remains a separate requirement.

### API and CLI

`run_all_18_design_gates(bundle, evidence_context=context)` accepts a context with
`manifest_path`, `trust_policy_path`, `expected_artifacts` (artifact ID to HTML path)
and `run_id`. The signed manifest has `render` and `review` envelopes, each with
`payload` and a base64 Ed25519 `signature` over UTF-8 canonical JSON (sorted keys,
compact separators, ensure_ascii=False, allow_nan=False). The policy schema is
`{"schema_version":1,"renderers":{"ID":"BASE64_RAW_PUBLIC_KEY"},"reviewers":{"ID":"BASE64_RAW_PUBLIC_KEY"}}`.
Keys identify separately authorized roles. Signature generation belongs to the
trusted renderer/reviewer processes, never to the untrusted deck producer.

The renderer payload contains schema_version, run_id, renderer_id, renderer,
capture_profile, and artifacts. Each artifact includes artifact_id, html_path,
html_sha256, png_path, png_sha256, width, height, resources=[], and
frame={selector,index,state}. Reviewer payload contains schema_version, run_id,
reviewer_id, render_payload_sha256, score_payload_sha256, reviewed_artifact_ids,
verdict, findings, and criterion_evidence. Each criterion observation names its
artifact_ids and a nonempty observation. All artifacts must be cited somewhere.

```text
python -B scripts/awf_design_anti_goodhart_gates.py --self-test
python -B scripts/awf_design_anti_goodhart_gates.py --audit-self
python -B design_tests/test_evidence.py
```

For final HTML-PPT acceptance, invoke its pinned script:

```text
python -B scripts/audit_single_slide_step.py --verify-deck-evidence deck.html --review-bundle bundle.json --evidence-manifest evidence.json --trust-policy trusted-public-keys.json --review-run-id RUN_ID --review-targets targets.json
```

The trusted runner must own the last three arguments and target mapping. Passing
attacker-chosen values there invalidates the trust boundary. See DesignAG
`references/evidence-contract.md` and source modules for the exact schema. Synthetic
fixtures create ephemeral in-memory keys and explicitly do not grant production trust.

All engineering scripts for this coordinated release are physically co-located at
`workflows/design-anti-goodhart/releases/1.0.0-rc.22/source/`; include that directory
and locked component trees when packaging. Current releases remain immutable.
